# E-Commerce-API

REST API интернет-магазина на FastAPI — каталог, корзина,
оформление заказа и онлайн-оплата.
Проект в разработке.

## Стек

Python 3.13 · FastAPI · Pydantic v2 · uv · Docker Compose · PostgreSQL 17 · Redis 7 ·
Ruff · mypy (strict) · pytest · GitHub Actions

## Что уже работает

- Приложение на FastAPI с фабрикой `create_app()` и эндпоинтом `GET /health`
- Конфигурация через pydantic-settings: обязательные поля без значений по умолчанию,
  приложение не стартует при неполном окружении
- Docker-образ: multi-stage, запуск от непривилегированного пользователя, 257 МБ
- `docker compose`: приложение, PostgreSQL 17 и Redis 7 с healthcheck'ами
- Проверки: Ruff, mypy в строгом режиме, pytest, pre-commit (включая поиск секретов)
- CI на GitHub Actions: три параллельные джобы — линтер, типы, тесты
- Асинхронный SQLAlchemy 2.0 + asyncpg, пул соединений с `pool_pre_ping`
- Alembic-миграции (async), первая — таблица `users`
- `GET /health/db` проверяет доступность базы, `GET /health` — только что процесс жив
- Единый формат ошибок RFC 9457 (Problem Details) и заголовок `X-Request-ID` на любом ответе
- Тесты гоняются на реальном PostgreSQL, изоляция — транзакция с SAVEPOINT на каждый тест
- Регистрация и вход: `POST /auth/register`, `POST /auth/login`, `GET /users/me`
- Пароли — argon2id (`pwdlib`), хэширование вынесено в отдельный поток, не блокирует event loop
- Access-токен — JWT (PyJWT, HS256), 15 минут жизни; в `/docs` есть кнопка Authorize
- Refresh-сессии: `POST /auth/refresh` с ротацией токена, детектом повторного
  использования и 10-секундным окном на ретраи; `POST /auth/logout` и `/auth/logout-all`
- Refresh уходит в httpOnly-cookie; в теле ответа — только при `AUTH_REFRESH_IN_BODY=true`
- Роли `customer`/`admin`, зависимость `require_admin`, `GET /users` только для админа
- Мгновенный отзыв access-токена через denylist по `jti` в Redis
- Ограничение частоты на `/auth/*`: 5 логинов в минуту, 3 регистрации в час, `Retry-After`
- `make create-admin email=...` — создание админа и повышение существующего пользователя

## Запуск

Нужны Docker и [uv](https://docs.astral.sh/uv/).

```bash
git clone git@github.com:MSFirsov/E-Commerce-API.git
cd E-Commerce-API
cp .env.example .env          # при желании поправить значения
make up                       # docker compose up -d --build
curl localhost:8000/health    # {"status":"ok"}
```

Документация API — http://localhost:8000/docs

Остановить: `make down`

### Локально, без контейнера приложения

База и Redis всё равно нужны, поэтому поднимаем их через compose, а приложение
запускаем на хосте:

```bash
uv sync
docker compose up -d postgres redis
uv run uvicorn app.main:create_app --factory --reload
```

В `.env` хосты указаны как `localhost` — это значения для запуска с хост-машины.
Внутри compose сервис `api` получает `POSTGRES_HOST=postgres` через `environment`.

### Команды

```bash
make lint                       # ruff check + ruff format --check
make typecheck                  # mypy
make test                       # pytest
make check                      # всё сразу — то же, что гоняет CI
make logs                       # логи приложения
make migrate                    # alembic upgrade head
make revision m="add orders"    # alembic revision --autogenerate
make downgrade                  # alembic downgrade -1
make db-shell                   # psql внутри контейнера postgres
make create-admin email=a@b.c   # создать админа (пароль спросит интерактивно)
```

## Структура

```
src/app/
  main.py            create_app() и lifespan
  core/
    config.py        настройки приложения
    db.py            async engine, session_factory, get_session
    deps.py          общие Depends (DbSession, AccessPayload, CurrentUser, AdminUser)
    errors.py        AppError и RFC 9457 Problem Details
    ratelimit.py     ограничитель частоты на Lua-скрипте в Redis
    redis.py         клиент Redis и Depends для него
    request_id.py    middleware + ContextVar для X-Request-ID
    security.py      argon2id, JWT, refresh-токены, denylist
  cli.py             команда create-admin
  models/            все SQLAlchemy-модели одним пакетом
  modules/           вертикальные срезы по доменам
    health/
      router.py
    auth/            регистрация, логин, refresh, логаут
      router.py
      schemas.py
      service.py
    users/           GET /me, GET / для админа
      router.py
      schemas.py
migrations/          Alembic (async), env.py, versions/
tests/
  conftest.py        тестовая БД и Redis, изоляция транзакцией с SAVEPOINT
```

Приложение построено как модульный монолит: каждый домен (каталог, корзина, заказы,
платежи) — отдельный пакет в `modules/` со своими роутером, схемами и сервисом.
Слоя репозиториев нет: `AsyncSession` в SQLAlchemy 2.0 уже реализует Unit of Work,
и дублировать его обёрткой значило бы добавить код без новых возможностей.

## База данных

Таблица `users`: `id` (UUID), `email` (уникальный), `password_hash`, `full_name`,
`role`, `is_active`, `email_verified_at`, `created_at`/`updated_at`. `role` — это
`VARCHAR(32)` с `CHECK`, а не нативный PostgreSQL ENUM: добавить новое значение
в ENUM — это блокирующая миграция таблицы, а `CHECK` меняется без блокировки и
значения видны прямо в `\d users`, без похода в `pg_enum`.

Таблица `refresh_tokens` — по строке на каждый выданный refresh-токен: `token_hash`
(`BYTEA`, sha256 от самого токена), `family_id` и `family_started_at`, `parent_id`
и `replaced_by_id` (ссылки на ту же таблицу — цепочка ротаций в обе стороны),
`issued_at`/`expires_at`/`used_at`/`revoked_at`/`revoked_reason`, плюс `user_agent`
и `ip` (`INET`) для списка активных сессий. `user_id` — с `ON DELETE CASCADE`:
удалили пользователя — его сессии ушли вместе с ним. Ссылки на соседей по цепочке —
`ON DELETE SET NULL`, чтобы чистка старых токенов не уносила живые.

Индексы: уникальный по `token_hash` (точный поиск при каждом обмене) и два частичных
с условием `revoked_at IS NULL` — по `user_id` и по `expires_at`. Частичные, потому
что отозванные строки запросам не нужны ни разу: индекс не растёт мусором, а
планировщик всё равно его использует, так как то же условие стоит в `WHERE`.

Первичный ключ — UUID (`gen_random_uuid()`), а не автоинкремент: id не выдаёт
количество заказов и пользователей конкурентам и не даёт перебирать чужие записи
по номеру. Плата за это честная — случайный UUID фрагментирует B-tree индекс
первичного ключа сильнее, чем последовательный `bigint`; на больших таблицах это
решается UUIDv7 (первые биты — таймстемп, вставки снова монотонны), но это уже
отдельная оптимизация, не обязательная на старте.

Пул соединений: `pool_size=5, max_overflow=10` на процесс — до 15 соединений
с базой от одного воркера uvicorn. Реальный лимит считается как
`(pool_size + max_overflow) × число процессов` и должен помещаться в
`max_connections` PostgreSQL с запасом на служебные подключения (миграции,
админ-доступ).

Тесты не используют `Base.metadata.create_all` — схема накатывается теми же
Alembic-миграциями, что и в проде, иначе тесты проверяли бы не то, что реально
задеплоится. Изоляция — одна внешняя транзакция на тест с `SAVEPOINT`
(`join_transaction_mode="create_savepoint"`): что бы тест ни закоммитил внутри,
после него всё откатывается, и тесты не зависят от порядка запуска.

## Аутентификация

Пароли хранятся как argon2id-хэш (`pwdlib`), а не bcrypt: у bcrypt пароль молча
обрезается до 72 байт, а argon2id — memory-hard функция, победитель Password
Hashing Competition, рекомендован OWASP. Хэширование стоит десятки миллисекунд
и намеренно тяжёлое — если считать его прямо в `async def`, это на всё это время
блокирует event loop и, как следствие, все остальные запросы приложения, поэтому
вызов вынесен в отдельный поток через `anyio.to_thread`.

Access-токен — JWT (PyJWT, алгоритм HS256), живёт 15 минут. В claims — стандартные
`sub`/`iat`/`exp`/`iss`/`aud`/`jti` (RFC 7519) и свои `typ`/`role`. `iss`/`aud`
проверяются при декодировании, чтобы токен, выпущенный тем же секретом для другой
цели, не прошёл; список разрешённых алгоритмов передаётся явно, а не берётся из
заголовка токена — иначе токен с `alg: none` прошёл бы проверку сам себя.
Токен проверяется ещё и по denylist в Redis (см. ниже), поэтому его можно отозвать
до истечения срока.

Ответ `/auth/login` на неверный пароль и на несуществующий email — один и тот же
код и тело. Без этого по разнице ответов (или по времени, если для несуществующего
email проверку пароля вообще пропустить) можно было бы перебором узнать, какие
email вообще зарегистрированы в системе, не имея ни одного пароля.

## Сессии, ротация и отзыв доступа

Refresh-токен — непрозрачное случайное значение (32 байта из `secrets`), живёт
30 дней. В базе лежит не он, а его sha256: утечка дампа не даёт ни одной рабочей
сессии. Пароли хэшируются argon2id, а токен — быстрым sha256, и это не
противоречие: argon2id намеренно медленный, потому что пароль человек
придумывает сам и его можно перебрать по словарю, а 256 бит случайности перебирать
нечем. Вторая причина — по хэшу нужен точный поиск по индексу на каждом обмене,
а argon2id со своей солью такого поиска не допускает.

Каждый обмен ротирует токен: старый гасится, выдаётся новый. Цепочка ротаций —
family; у неё свой `family_id` и свой срок. Поверх скользящих 30 дней на токен
действует абсолютный срок семьи — 90 дней от логина. Активный пользователь не
разлогинивается никогда, но сессия, начатая однажды, не живёт дольше трёх месяцев
ни при каком количестве обменов.

Повторное предъявление уже использованного токена отзывает всю семью целиком,
включая актуальный токен. Отличить вора от жертвы в этот момент невозможно —
кто-то из двоих предъявил старое значение, и правильный исход один: оба идут
логиниться заново. Ложные срабатывания (две вкладки обновились разом, клиент
переотправил запрос после обрыва сети) закрывает окно в 10 секунд: повторный обмен
внутри него возвращает ту же пару, что была выдана, если совпадает `User-Agent`.
Пара на это время лежит в Redis — в базе её взять нельзя, там только хэш.

Транспорт — httpOnly-cookie с `Secure`, `SameSite=Lax` и `Path=/auth`. `httpOnly`
закрывает чтение токена из JavaScript (а значит, и кражу через XSS), `Secure`
запрещает отправку по http, `SameSite=Lax` не даёт браузеру приложить cookie
к межсайтовому запросу (CSRF), `Path=/auth` — к любому запросу, кроме эндпоинтов
аутентификации. Флаг `AUTH_REFRESH_IN_BODY=true` дополнительно кладёт токен в тело
ответа: это режим для Postman и мобильных клиентов, и в браузере он обнуляет пользу
`httpOnly`, поэтому по умолчанию выключен.

Роли — `customer` и `admin` в `VARCHAR(32)` с `CHECK`; анонимный запрос
получает `401` («ты кто?»), запрос с валидным токеном и недостаточной ролью — `403`
(«вижу кто, но нельзя»). Access-токены живут 15 минут и ничего не знают о базе,
поэтому `logout-all` гасит текущий через denylist: `jti` кладётся в Redis с TTL,
равным остатку жизни токена, и проверка денилиста стоит в самой зависимости,
которая разбирает заголовок `Authorization`, — то есть на каждом защищённом
эндпоинте. Остальные устройства при этом теряют refresh сразу, а access доживают
свои 15 минут.

Массовая инвалидация всех access-токенов пользователя одним ключом
`revoked_before:<user_id>` пока не сделана — у неё дешевле проверка, но нужна
аккуратность с часами.

Ограничение частоты на `/auth/*` — фиксированное окно в Redis, инкремент и
установка TTL одним Lua-скриптом, чтобы между ними не влез другой запрос:
5 логинов в минуту и 3 регистрации в час на IP, в ответе `429` с `Retry-After`.
Лимит считается по IP; счёт по email вдобавок к IP — следующий шаг, он закрывает
распределённый перебор одного аккаунта.
